# Architecture

```
Browser ──▶ web (Next.js) ──rewrites /api, /_allauth, /django-admin──▶ api (Django + gunicorn)
                                                                        │
                                                        ┌───────────────┼───────────────┐
                                                     Postgres         Redis        worker / beat (Celery)
                                                                  cache, sessions,    emails, hold expiry,
                                                                  rate limits, queue  cache revalidation
```

## Why one origin

The browser only talks to the web service. Next.js rewrites `/api/*`, `/_allauth/*` and `/django-admin/*` to Django over Railway's private network. The benefits:

- **Auth cookies stay first-party.** The Django session and CSRF cookies are `httpOnly`, `Secure` and `SameSite=Lax`, so no auth token ever lives in `localStorage`.
- **No CORS setup.** Nothing to configure or get wrong.
- **One public service.** Only the web service needs a public domain. The Stripe webhook reaches Django through the same rewrite.

Server Components call Django directly (`API_ORIGIN`) and forward the incoming request's cookies.

## API (`api/`)

- **Settings:** split into `config/settings/{base,dev,test,prod}.py`, with every secret read from the environment through django-environ.
- **Apps:** each app under `apps/` keeps views thin. Writes and business rules live in `services.py`, and optimized reads (`select_related`/`prefetch_related`) live in `selectors.py`.
- **Schema:** the OpenAPI schema is generated by drf-spectacular (`/api/schema/`, browsable at `/api/docs/`). The web app's TypeScript client is generated from it, and CI fails if they drift.
- **Redis:** backs the Django cache (public catalog responses, invalidated on write), cached-db sessions, rate limits and the Celery broker.
- **Health check:** `/api/v1/health/` checks both Postgres and Redis. Railway uses it as the deploy health check.

## Web (`web/`)

- **App Router and Server Components** render public pages for SEO.
- **Client state:** TanStack Query handles client-side mutations.
- **Components:** all UI components are shadcn/ui in `src/components/ui`, themed with the original TrailVenture tokens in `src/app/globals.css`, in light and dark.
- **Deployable output:** `output: "standalone"` builds a small Node server for the Docker image.

## Booking and payment

Prices are decided by the server and never by the client. The flow mirrors the original site:

1. **Quote.** The booking card asks `POST /api/v1/bookings/quote/` for a breakdown: base price, site fee
   and tax, taken from the tier and the single active `FeeSchedule`. Every amount is an integer number
   of centavos, so nothing is lost to floating point.
2. **Hold.** `POST /api/v1/bookings/create/` writes the booking with its own copy of those amounts and
   a 30-minute `hold_expires_at`. The snapshot means a later price change cannot alter a booking that
   is already being paid for.
3. **Checkout.** `POST /api/v1/bookings/{id}/checkout/` creates a Stripe Checkout Session in PHP
   centavos, keyed by an idempotency key of `booking-{id}`, so a repeated request returns the same
   session rather than charging twice. Without Stripe keys the endpoint answers 503 and the page says
   payments are unavailable.
4. **Webhook.** `POST /api/v1/payments/stripe/webhook/` verifies the Stripe signature, then records the
   event id before doing anything: a replayed event is recognised and ignored. Completed and
   asynchronously succeeded payments confirm the booking; expiry and failure release it; a refund marks
   it refunded. Unexpected errors are allowed to return 5xx so Stripe retries.
5. **Result pages.** Because confirmation arrives by webhook and not in the redirect, `/booking/success/[id]`
   polls the booking until it is confirmed and says so plainly if that takes more than a minute. The
   cancelled page offers to reopen the same checkout session while the hold is still alive.

Nothing deletes a booking. Unpaid holds are expired by the Celery beat task `expire-stale-booking-holds`,
which runs every five minutes.

## Reviews and profile photos

A review belongs to a **booking**, not to a package. That is what makes it trustworthy: the API
only accepts one from the traveler who owns a paid booking whose start date has passed, and only
once per booking. Saving a review recomputes the package's `rating_avg` and `rating_count` and
bumps the catalog cache version, so cards, filters and JSON-LD follow along. Hidden reviews drop
out of both the list and the rating, which is what the Phase B moderation tools will use.

Profile photos never pass through Django. The API signs an upload for one public ID it chooses
itself — `trailventure/accounts/avatars/<user id>` — the browser uploads the file straight to
Cloudinary, and then tells the API which version to show. A client cannot point its profile at
someone else's image, because it never supplies the key. The version is part of the stored key,
so a replaced photo gets a fresh URL instead of a cached copy of the old one. Without
`CLOUDINARY_URL` the signing endpoint refuses and the account page hides its photo controls.
